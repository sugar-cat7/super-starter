# Cloudflare local development and deployment

Each Worker owns one `cloudflare.config.ts`; Vite+ and the Cloudflare Vite plugin generate runtime types and Build Output. Do not hand-maintain Wrangler config alongside it. `local`, `dev` and `production` are explicit SDK environments; unknown names fail. Vite reserves the name `local`, so scripts pass Vite mode `offline`, mapped explicitly to SDK `local`. The cf type command uses SDK mode `local` directly.

## Project-local cf operations

Use `pnpm cf <command>` inside the owning Worker, or `pnpm --filter <scope>/<worker> cf <command>` from the repository root. This invokes the installed official CLI without adding a dispatcher or global tool. Setup installs it only for selected Workers; Desktop/library presets have no cf command. Run project commands where `cloudflare.config.ts` exists: the CLI can otherwise auto-configure an uninitialized directory and install packages.

| Operation                | Standard entry and responsibility                                                                                                                                                                                                                                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Development              | API `pnpm dev` invokes `cf dev --mode offline`; TanStack Web uses the direct `vp dev --mode offline` entry because cf beta.14's framework detector rejects its Vite mode. Root startup prepares selected resources/dependency order. Host, port, state and strict-port behavior live in Vite configuration.                                                                    |
| Build                    | The existing cancellable `pnpm build` helper uses `cf build --mode offline` for APIs and direct `vp build --mode offline` for TanStack Start. `STARTER_BUILD_MODE=dev` is used only by checked dev preflight. cf delegates to the installed v2 plugin; project-local Vite+ supplies its Vite core.                                                                             |
| Types                    | `pnpm typegen` invokes `cf workers types -m local`. The SDK/plugin generates the same runtime/binding types during development/build.                                                                                                                                                                                                                                          |
| Discover resources/API   | `pnpm cf cli search "<action and resource type>"`, then the returned command's `--help`; replace its leading `cf` with `cf schema` for request schema. Use anonymous queries, never names/domains/IDs/tokens. Installed commands cover D1/KV/R2, Workers, logs, secrets and other account resources; permission and approved target still govern each actual remote operation. |
| Authentication           | Use an existing approved profile/token. `pnpm cf auth whoami` inspects that identity; interactive login is an explicit user setup action. Tokens belong in the existing secret store/ignored file, never source or browser bundles.                                                                                                                                            |
| Local D1 preparation     | `pnpm db:migrate` / `pnpm db:seed` derive a disposable local-only Wrangler config from SDK Build Output. cf beta.14 `d1 migrations apply --local` still applied SQL but did not terminate in the 2026-10-11 compatibility probe; keep this narrow fallback until an official fix passes completion, repeat and shared-state tests.                                             |
| Local built HTTP preview | `pnpm preview` uses the SDK-derived Wrangler adapter for the exact built module/asset manifest. `cf previews deploy` uploads a remote preview and is not this credential-free local check. cf has no equivalent local prebuilt-preview command in the adopted interface.                                                                                                       |
| Validate/deploy          | `pnpm deploy:preflight` checks the named target/environment. The existing authorized-dev `pnpm deploy` entry invokes `cf deploy --prebuilt --no-provision -m dev`, then records the actual artifact and approved health smoke. cf's direct `deploy` can provision resources and is not a substitute for that checked delivery entry.                                           |

cf beta.14 rejects the stable v1 Vite plugin for dev/build. The catalog therefore pins the official `2.0.0-beta.sha-91c870c02` release after minimal compatibility verification; the obsolete v1 `experimental.newConfig.cfBuildOutput` flag is removed. Vite+ remains the single local Vite owner. Root startup sets `CLOUDFLARE_REGISTRY_PATH` alongside the existing Wrangler/Miniflare keys, so cf cannot replace the owned lifecycle registry with a global default. The [adoption record](adoption.md) distinguishes the initial failing probes from the accepted input. D1 and built-preview fallbacks are the only normal Wrangler CLI paths; they do not introduce a second authored configuration.

Actual selected Web setup also rejected `cf build --mode offline` with `The detected command npx vite build does not currently support --mode.` The CLI's TanStack framework metadata does not expose the Vite mode support and its workspace command detection defaults to npx. Keep Web dev/build on the declared Vite+ CLI until the official adapter passes this project's named-mode/workspace checks; do not patch SDK detection, install a global Vite or hide the framework dependency. Its configuration/types/resource operations and checked prebuilt deployment still use the same cf SDK/CLI.

After the selected Workers are built offline, `pnpm --filter <scope>/<worker-directory> preview` serves its actual production output through local Wrangler HTTP. The four-line adapter imports its own config SDK and calls `tools/cloudflare/preview.ts`, which derives disposable `.cloudflare/preview.wrangler.json` from Build Output. SDK conversion owns Binding/environment mapping; the helper only supplies the built module manifest and assets directory. The [Lighthouse runner](lighthouse.md) builds and starts the selected dependency graph automatically, preserving real static-asset compression and cleaning up its disposable state and servers.

Selected D1/KV/R2 produce only those bindings. D1's deterministic local UUID, migrations, seed and dev runtime use the same `.state/<directory>`; setup migrations are repeatable, and initial seed is not replayed after deletion. Cloud-free tests use actual workerd; no accounts/tokens are needed. Volatile configurations say that their data resets. Fullstack Web depends on the API's manifest package for ordering, and communicates by Service Binding rather than code import. Both local root startup and CI start the API before Web. Desktop's adapter stays offline.

Remote artifacts deny unauthenticated writes and have no default workers.dev/preview publication. Configure existing approved dev resources: `CLOUDFLARE_ACCOUNT_ID`, selected `D1_DATABASE_ID`, `KV_NAMESPACE_ID`, `R2_BUCKET_NAME`, plus a narrowly scoped `CLOUDFLARE_API_TOKEN` only for an authorized deployment. Use your existing secret store or an ignored local environment file; never embed tokens into Web/Desktop or print their values. Supply environment variables explicitly to the command. Unknown/missing IDs fail; no resource provisioning/fallback is performed. Add an explicitly approved dev custom domain with the SDK worker.domains field in the sole config before remote smoke. For example, conditionally set domains to your approved per-target domain only in environment dev; keep local without domains and workersDev false. Configure API and Web domains separately.

Run `pnpm deploy:preflight -- --target api --environment local` for credential-free local validation; it runs quality, tests, actual runtime and build, then records the input/artifact. Use environment `dev` for connection preflight. Missing account/resources fail with configuration guidance, and are not a deployment success. `pnpm deploy -- --target api --environment dev --smoke-url https://<approved-api-domain>/health` requires the user's authorized dev environment and credentials, deploys only the newly checked prebuilt artifact with auto-provisioning disabled, and never runs from setup/build or ordinary CI. Deploy API first, smoke the explicitly configured dev route, then Web. The standard deploy entry records the deployed artifact and successful health smoke per package/account/input. Deploy Web with the same entry and its own approved /health URL; it checks the upstream receipt, current built artifact/config and health before changing Web. Stale/failed receipts or changed resource settings stop it. A failed post-deploy smoke is recorded as deployed but not verified; inspect that receipt before retrying. `pnpm deploy -- --target <worker> --environment local --dry-run` runs local preflight only and performs no remote operation. No undeclared environment or production fallback is allowed. Clean up only temporary resources created for that authorized rehearsal; never replace/delete existing resources.

If choosing Workers Builds instead of manual dev delivery, set repository root as root directory, build command to `mise install && pnpm install --frozen-lockfile && pnpm env:setup && pnpm gate:pre-pr -- --base <base-sha>`, then build the explicit Worker in mode `dev`. Set its deploy command to the standard dev deploy entry for that package and approved smoke URL, supply the same named-account/resource settings and narrow token, and configure API-before-Web order. Watch the owning package, its shared dependencies, tools, root configs, catalog and lockfile. Do not configure a second Actions deployment. This repository's ordinary Actions workflows perform checks only.

Actual Cloudflare deployment, remote Binding connectivity, domain routing, credentials and Renovate/GitHub App connection require external setup and are not claimed by a local build. Production delivery and signed public Desktop releases are separate work.

Windows process cleanup uses the OS Job Object API, not PID ancestry snapshots. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) were read on 2026-10-09. A child is created suspended with atomic Job membership using the documented [PROC_THREAD_ATTRIBUTE_JOB_LIST](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), then resumed; nested descendants retain ownership when intermediate parents exit. A thin PowerShell/C# adapter uses standard kernel32 APIs without elevation or execution-policy changes. Its real orphan/sentinel regression runs through the ordinary tools test command on each OS. Linux passed; Windows adoption remains provisional until the required Windows job actually executes.

Actual Windows Server 2025 CI exposed a defect in the orphan fixture: Node's [pinned libuv implementation](https://github.com/nodejs/node/blob/v24.21.0/deps/uv/src/win/process.c) assigns non-detached children to a parent-owned kill-on-close Job, so `unref()` does not keep the fixture server alive after its intermediate parent exits. The fixture uses `detached` only on Windows; POSIX retains its existing process group. libuv does not request Job breakaway, so the server remains owned by the outer Starter Job. Original live-server, cleanup and unrelated-sentinel assertions remain required on Windows. A separate Worker interruption fixture's hidden startup failure is not yet diagnosed; it now records bounded output, early exit and relevant executor key spellings under the same ten-second deadline. No Job adapter change or deadline increase is inferred from a missing address. These Node [detached/environment APIs](https://nodejs.org/download/release/v24.21.0/docs/api/child_process.html) and source were checked on 2026-10-10 UTC. Selected Binding runtime tests also retain unexpected GET bodies in failure diagnostics, without changing the expected status or payload.

The next real Windows run identified that separate fixture failure: inherited `NPM_EXECPATH` won Node's lexicographic, case-insensitive child-environment deduplication over the added `npm_execpath`. Spreading even the special Windows `process.env` into an ordinary object permits this collision. The fixture removes every alias before assigning its executor; production process ownership, expectations and deadlines are unchanged. Actual repaired Windows success remains required.

Hosted macOS release startup succeeded but cleanup's signal-zero probe failed with `EPERM`. Apple's current [XNU killpg implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c) excludes zombie processes for every signal and can return `EPERM` for a zombie-only group. A Darwin-only fallback uses the documented [ps fields/states](https://github.com/apple-oss-distributions/adv_cmds/blob/main/ps/ps.1): a bounded, complete, validated process table must show no live member of the exact owned process group. This also handles an already stopped group at the initial SIGTERM or the final SIGKILL race. Live members, malformed/failed probes and actual termination permission errors still fail. Regression fixtures supplement, rather than replace, real orphan/sentinel and macOS native checks. Official implementation and SDK sources were read on 2026-10-10 UTC.

Real Windows revalidation must establish the fix; no request replay, transport rewrite, dependency patch or timeout extension is used. Owned registry paths and unexpected HTTP bodies are retained in test diagnostics. Sources were checked on 2026-10-10 UTC.

Actual Windows Git-hook CI on 2026-10-10 completed the valid pushed-commit gate, then failed while Git deleted its owned temporary worktree: `Filename too long`. The runner's Git for Windows 2.55.0.windows.5 [recursive worktree removal](https://github.com/git-for-windows/git/blob/v2.55.0.windows.5/builtin/worktree.c) and [Windows filesystem implementation](https://github.com/git-for-windows/git/blob/v2.55.0.windows.5/compat/mingw.c) follow `core.longpaths`. Owned hook and rehearsal worktree removal therefore uses the official [command-scoped configuration](https://git-scm.com/docs/git#Documentation/git.txt--cltnamegtltvaluegt), `git -c core.longpaths=true worktree remove --force`, without changing user/global configuration or OS permissions. The subsequent real Windows regression found that Git deliberately preserves [junctions and their ancestors](https://github.com/git-for-windows/git/blob/v2.55.0.windows.5/dir.c#L3462) even when removal succeeds and unregisters the worktree. After successful Git removal only, Node's [pinned synchronous removal](https://github.com/nodejs/node/blob/v24.21.0/src/node_file.cc#L1748) finishes that same owned snapshot using a namespaced path and `std::filesystem::remove_all`. The [Microsoft STL implementation](https://github.com/microsoft/STL/blob/main/stl/inc/filesystem) treats junctions as links to remove rather than directories to traverse; the exact STL revision in the Node binary is not recorded, so the real Windows sibling-sentinel regression remains the required compatibility proof. Locked-worktree and other Git failures prevent this filesystem step; filesystem errors also propagate. Cleanup errors remain errors. Real deep-path/junction/locked-worktree regressions protect sibling data and configuration; the actual push rehearsal checks both physical cleanup and Git registration after accepted, rejected and repaired pushes. Which dependency leaf triggered the original error was not recorded. Final Windows execution must verify the repaired input; earlier native/fault success does not turn the failed job into a pass.
